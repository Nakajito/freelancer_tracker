Security

Effective: May 11, 2026

1. Introduction

PropoTrack is committed to protecting the data of freelancers who trust us with their proposals, clients, and time records. We apply layered defenses across the application, transport, and infrastructure layers. The practices described on this page reflect the current implementation and evolve continuously.

2. Authentication & Sessions

Accounts are created with an email address and password via django-allauth. Login is email-only (ACCOUNT_LOGIN_METHODS = {"email"}). Sessions are stored server-side in the database — no JWTs, no tokens in localStorage. Session cookies are HttpOnly, Secure, and SameSite=Lax in production, with an 8-hour idle timeout. Password changes are available at /.well-known/change-password.

3. Password Storage

Passwords are hashed with Django's default algorithm (PBKDF2-SHA256). Active validators include UserAttributeSimilarityValidator, MinimumLengthValidator (minimum 8 characters), CommonPasswordValidator, and NumericPasswordValidator. Passwords are never stored or transmitted in plaintext.

4. Transport Security (HTTPS/TLS)

HTTPS is enforced in production via SECURE_SSL_REDIRECT. HTTP Strict Transport Security (HSTS) is active with max-age=31536000 (1 year), includeSubDomains, and preload. The following response headers are applied in production:

Header Value
Strict-Transport-Security max-age=31536000; includeSubDomains; preload
X-Content-Type-Options nosniff
X-Frame-Options DENY
Referrer-Policy same-origin
Cross-Origin-Opener-Policy same-origin

5. Application-Layer Defenses

Cross-Site Request Forgery tokens are present in all POST forms, with Secure, HttpOnly, and SameSite=Lax cookies. A strict Content Security Policy is applied in production: default-src 'self', no arbitrary inline scripts, and frame-ancestors 'none'. Django templates auto-escape all output by default, preventing XSS at the rendering layer. No third-party tracking or analytics scripts are loaded.

6. Per-User Data Isolation

Every domain model inherits from OwnedModel, which adds a mandatory owner foreign key to the user. Isolation is enforced at two levels:

  • QuerySet layer — all views and services filter by owner=request.user via OwnerQuerysetMixin or ProposalOwnerQuerysetMixin. A user can never query another user's proposals, clients, time entries, or templates.
  • API layer — all REST endpoints require IsAuthenticated permission. No public read endpoints expose user data.

The ActivityLog model uses a generic foreign key so signals from any app can record domain events without coupling the audit table to specific models.

7. Data Storage

In production, data is stored in PostgreSQL 16 with credentials sourced from environment variables and connections encrypted over TLS. No payment card data is stored — financial amounts are decimal values entered manually by the user. User data is not shared with or sold to third parties. Application-level isolation (Section 6) ensures logical separation between accounts.

8. Secrets & Configuration

All sensitive configuration (secret keys, database credentials, SMTP credentials) is loaded via django-environ from environment variables. DJANGO_SECRET_KEY is required in production with no default value. DEBUG=False is enforced in production. The repository does not contain a .env file (only .env.example is committed).

9. Webhook Integrity

The webhook endpoint at /api/webhooks/proposal-events/ validates payloads using HMAC-SHA256. The signature is compared with hmac.compare_digest, which is resistant to timing attacks. Requests with an invalid or missing signature are rejected with a 401 Unauthorized response.

10. Audit Trail

The ActivityLog model records domain events — proposal status changes and follow-up completions — via Django signals. Django security events are emitted to the django.security logger at the WARNING level and above in production, making them visible in infrastructure logs for review.

11. Infrastructure

The application runs in a minimal multi-stage Docker container. The application process runs as a non-root user, reducing the escalation surface. A health check endpoint is exposed at /healthz. Deployments run via Coolify with DJANGO_SETTINGS_MODULE=config.settings.prod enforced. The stack is monitored and updated on a regular schedule.

12. Responsible Disclosure

If you discover a security vulnerability, please report it to security@dabg.dev. The full contact details and scope are also available in the standard security.txt format. We are committed to responding within 5 business days and will not pursue legal action against good-faith security research (no destructive scanning, no accessing other users' data, no denial-of-service).

Languages accepted for disclosure: Spanish, English.

13. Continuous Improvement

We evaluate and continuously improve our security practices. This page will be updated as new controls are added. The effective date at the top of the page indicates the current version.
