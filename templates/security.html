{% trans "1. Introduction" %}

{% blocktrans %}Pipelancer holds your pipeline: who you pitched, for how much, and what you earned. This page describes the controls that protect it, at the application, transport and infrastructure layers. It reflects what is actually implemented rather than what is aspirational, and it is updated as controls change.{% endblocktrans %}

{% trans "2. Authentication and sessions" %}

  • {% trans "Email and password sign-in via django-allauth. Email is the only login identifier and must be verified before the account can be used." %}
  • {% trans "Sessions are stored server-side in the database. No tokens are kept in localStorage." %}
  • {% trans "Session cookies are HttpOnly, Secure and SameSite=Lax, expire after 8 hours, and are cleared when the browser closes." %}
  • {% trans "Repeated failed sign-ins lock the account and source address combination for one hour." %}
  • {% trans "Sign-in, sign-up and password reset are protected by a CAPTCHA, which rejects attempts rather than letting them through if it cannot be reached." %}
  • {% trans "Changing your password is available at" %} /.well-known/change-password.

{% trans "3. Password storage" %}

{% blocktrans %}Passwords are hashed with Argon2, a memory-hard algorithm. Four validators apply: similarity to your account details, a minimum length of 8 characters, a common-password list, and a numeric-only check. Passwords are never stored or transmitted in the clear, and we cannot read them.{% endblocktrans %}

{% trans "5. Application-layer defences" %}

  • {% trans "CSRF tokens on every state-changing request, with Secure, HttpOnly, SameSite=Lax cookies." %}
  • {% trans "Templates escape output by default; no raw HTML injection points are used anywhere in the interface." %}
  • {% trans "All database access goes through the ORM with parameterised queries." %}
  • {% trans "Uploaded files are validated by type, size and dimensions, and stored under generated names." %}
  • {% trans "Exported spreadsheets neutralise cells that would otherwise be interpreted as formulas by Excel or Sheets." %}
  • {% trans "No third-party analytics or tracking scripts are loaded." %}

{% trans "6. Per-user data isolation" %}

{% blocktrans %}Every record belongs to exactly one account. Isolation is enforced at the query layer, so a request for another user's proposal, client, template, follow-up or time entry cannot return data regardless of how the identifier is supplied. This is covered by an automated test suite that asserts the behaviour for every such route, so a regression fails the build rather than reaching production.{% endblocktrans %}

{% trans "7. Data storage" %}

{% blocktrans %}Production data lives in PostgreSQL 16, with credentials supplied through environment variables and never committed. We do not store card numbers or bank details: donation payments are handled entirely by the payment provider, and we retain only an amount, a status and a provider reference.{% endblocktrans %}

{% trans "8. Secrets and configuration" %}

{% blocktrans %}All sensitive configuration is loaded from environment variables. Production requires an explicit secret key with no fallback, and runs with debug mode off. The repository is scanned on every change for committed credentials, known-vulnerable dependencies, and insecure code patterns; these checks block the build rather than merely reporting.{% endblocktrans %}

{% trans "9. Payment webhook integrity" %}

{% blocktrans %}Incoming payment notifications are authenticated with an HMAC signature over the resource identifier, request identifier and timestamp, compared in constant time. Signatures expire, so a captured notification cannot be replayed, and a signature issued for one resource cannot be used against another. Payment status is always re-read from the provider rather than taken from the notification body.{% endblocktrans %}

{% trans "10. Audit trail" %}

{% blocktrans %}Domain events such as proposal status changes are recorded with an actor and a timestamp. Security-relevant events are emitted to a dedicated log channel at warning level and above.{% endblocktrans %}

{% trans "11. Infrastructure" %}

{% blocktrans %}The application runs in a minimal multi-stage container as an unprivileged user, with development and test tooling excluded from the production image. Build inputs are version-pinned and verified. A health endpoint is exposed for monitoring, and the base image and dependencies are updated on a weekly schedule.{% endblocktrans %}

{% trans "12. Responsible disclosure" %}

{% blocktrans %}If you find a vulnerability, report it to{% endblocktrans %} security@dabg.dev. {% blocktrans %}The same channel is published in standard format at{% endblocktrans %} /.well-known/security.txt.

{% blocktrans %}We aim to respond within five business days, and we will not pursue legal action over good-faith security research. Please do not run destructive scans, access other users' data, or degrade the service for others while testing. We can correspond in Spanish or English.{% endblocktrans %}

{% trans "13. Continuous improvement" %}

{% blocktrans %}Security is not a fixed state. We review these controls regularly and strengthen them as the product grows; this page is updated when they change, and the effective date above indicates the current version.{% endblocktrans %}
